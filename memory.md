## What it is
Landing page for Fabricio's personal challenge: help 100 people solve real problems for free using AI as the tool (not the product). Claude Design (dc) component + Firebase + EmailJS. Live at project100.dev.

## Key decisions
- AI is positioned as the tool, not the product — all copy leads with the problem, never the technology. This is a deliberate brand choice, not a style preference
- Full redesign using Claude Design (dc) component architecture — index.html is now a .dc.html file rendered via React runtime (support.js). GSAP and the old style.css/form.js/main.js are no longer used by the landing page (kept in repo but unused)
- Form reduced from 6 steps to 4: name, email, problem, phone. Business type and revenue steps intentionally removed
- Counter updated to 7 completed / 1 in progress / 92 spots left
- Second testimonial added: Martina S. from MRL event ticketing
- Grid of 100 cells added to hero — each cell has a hover tooltip; open cells open the form on click

- 2026-09-29: Investigated "#open-form doesn't open the form." Two separate bugs stacked:
  1. The June 30 redesign never ported the `#open-form` hash-check from the old form.js into the new React component's componentDidMount. Added `if (window.location.hash === '#open-form') this._openForm();` (index.html).
  2. Much bigger: the whole form had been broken since 2026-07-03 (not just the hash link — the "Join the 100" button too). The July 3rd fix for the GitHub secret-scan alert moved `firebaseConfig` into a gitignored file, but this is a static GitHub Pages site with no build step, so that file was never deployed. `firebase.initializeApp(firebaseConfig)` threw on every page load, which made `_startSession()` throw, which aborted `_openForm()` before it ever set `open: true`. Confirmed with a headless-browser test against the live site (Playwright) — reproduced the exact console errors, then reproduced the fix working.
  Fix: restored the Firebase config to committed source (un-gitignored `3. Scripts/firebase-config.js`) and removed it from `.gitignore`. Firebase web app config is not a real secret — it only identifies the project to the client SDK; actual access control is Firestore security rules (already locked down for admin reads since 2026-06-21). Re-verified live with Playwright after deploy: both the hash link and the button now open the form with zero console errors.
  **Lesson for next time a "secret" gets flagged on this project:** don't gitignore config that the deployed static site needs at runtime — there's no build step to inject it back in. Check Firestore rules instead.

  Also investigated: admin.html was "very slow, keeps loading." First guess was unbounded reads (every form-open click writes a session doc via `_startSession()`, and `loadDashboard()` pulled the whole collection with no date limit) — added a 90-day `where('startedAt', '>=', ...)` filter on the sessions query. **This guess was wrong and broke the dashboard completely** (permission-denied on every load) — reverted same day. The real cause, found via the actual browser console: the Firestore rules had no `match` block at all for `ai-business-ads` or `p100-projects`, so those reads were always silently denied (Firestore denies anything not explicitly matched), which failed the whole `Promise.all` in `loadDashboard()` regardless of the sessions query shape. This was very likely the real cause of the original complaint too, not data volume. Fixed by having Fabricio add `allow read, write: if request.auth != null;` blocks for both collections in the Firebase Console (Firestore → Rules) and publish. Also added a try/catch around `loadDashboard()`'s Promise.all so a future failure shows an error message in the header instead of hanging on "Loading..." forever with no clue why.
  **Lesson:** when Firestore data "won't load," check the actual browser console error before guessing — "Missing or insufficient permissions" and "slow because of data volume" look identical from the outside (both just hang), but are completely different problems with completely different fixes. Don't diagnose Firestore issues from code reading alone when a live authenticated test is possible.
